# 16 导图渲染选型（Web + Android）

> 一句话：**Web 端用 markmap（MIT，只读渲染），Android 端继续用自研 `MindMapGraphView`，不引库。**
> 两端都不缺"能画图的库"，缺的是对"一页书 1~22 个根节点"这种数据的布局策略——这是数据问题，不是选型问题。

本文所有版本号、star 数、体积、许可，都是 2026-11-16 现查现测的结果；标"实测"的数字是本机跑出来的，不是文档里抄的。

---

## 0. 结论先行

| 端 | 选型 | 理由 | 代价 |
|---|---|---|---|
| Web（`tools/webeditor`） | `@markmap/view` + `@markmap/render`，**不走** `@markmap/parse` | 唯一原生支持多根的库；MIT；tree 布局 + cards 主题最接近 App 现有节点块；离线打包无外部请求 | 生产产物 +351KB / gzip +116KB（已接入） |
| Android（`app`） | 保留 `MindMapGraphView`，不引库 | 现有实现已支持多根 / 折叠 / 字号档 / 双指缩放，且吃 `values/` 里的设计令牌；市面上的库**全部要求单根** | 需要自己补夜间配色与性能细节 |
| 两端"完全同款"（可选） | Android WebView 内嵌同一份 markmap 产物 | 唯一能做到像素级一致的路 | 首屏 +200~400ms、内存 +30~60MB、主题与手势要桥接；不推荐做主路径 |

## 1. 约束（从代码里量出来的，不是假设）

| 项 | 现状 | 对选型的影响 |
|---|---|---|
| Android | minSdk 24 / compileSdk 35 / 原生 View（无 Compose） | 排除 minSdk 28+ 的库；Compose 库不可用 |
| Android 依赖 | 除 OkHttp 外全是 AndroidX | 引入任何库都要能说清楚"为什么值得" |
| Web | Vue 3 + TSX（禁模板）/ Vite / 打包进 `assets/webeditor` | 库必须框架无关；bundle 直接进 APK |
| Web 体积 | 编辑器产物 643KB（`assets` 合计 2.3MB） | gzip +116KB 可接受，+1MB 不可接受 |
| 运行环境 | 局域网离线，无 CDN | 所有依赖必须本地打包 |
| 数据规模 | 11 板块 / 41 主题 / 1194 节点；单页最多 51 节点、最深 5 层 | 不需要虚拟化/Canvas 级性能 |
| **根的个数** | 中位数 **5**，最大 **22**；41 个主题里 **26 个 >3 根** | **决定性约束**：绝大多数库假设"一个中心主题" |

最后一行是关键。现有资产是从书页 OCR 还原的，一页书常被切成好几个"中心主题"（`分配` / `制` / `度` 各算一个根），所以"多根"不是异常，是常态。

### 2.1 markmap 的三个坑（都实测过）

1. **包名换了**：`markmap-view@0.18.x` 已标记 deprecated（"Replaced by `@markmap/*` in 1.0.0"）。必须用 `@markmap/view` / `@markmap/render` / `@markmap/core`，网上大量教程还是 0.18 的写法。
2. **`theme` / `layout` 传字符串会崩**：`theme: 'classic'`、`layout: 'org-chart'` 会抛 `layout is not a function`。1.x 的选项是**对象**，要 `import { cardsTheme, treeLayout } from '@markmap/render'` 再传进去；字符串形式是给 frontmatter 用的，需要额外注册。
3. **别引入 `@markmap/parse`**：它是 markdown → 树的解析器（unified/remark），实测多 69KB gzip；而且我们的正文里有 `（2012）`、`、`、`·`、`#` 这类字符，走 markdown 还要处理转义。直接用它的节点结构更省更稳：

```ts
// 资产 → MarkmapNode，不走 markdown
type MMNode = {
  id: string
  type: 'root' | 'heading' | 'listItem'
  content: { type: 'text'; value: string }[]
  notes: never[]
  data: Record<string, unknown>
  children: MMNode[]
}

// 多根 → 一个虚拟根（type=root、content 为空，markmap 不画它）
// 或者用主题名当可见根，见 2.2
```

实测多根在 markmap 内部就是这个表示：`parse('# a\n# b')` 得到 `{type:'root', content: [], children:[H1, H1]}`。

### 2.2 一个布局实测：多根会竖着串起来

| 组合 | 结果 |
|---|---|
| 虚拟根（无内容）+ tree | 19 个根竖排成一列，整图又高又窄，fit 之后字约 4px |
| **主题名当可见根** + tree + cards | 有中心块，分支向右铺开；仍是"高瘦"型，但结构能看懂 |
| org-chart | 19 个子节点横排，宽度爆掉，fit 后压成一条线（不可用） |
| two-sided | 分支分两侧，仍然过宽（不可用） |

所以 Web 端的接入姿势是：**主题名当根，原各根变成第一层子节点**，配 `treeLayout + cardsTheme`，默认 `foldLevel: 2` 左右，让用户先看到骨架再展开——和 App 大纲页"默认全折叠"是同一个思路。

## 3. Android 候选横评

先给一个事实：GitHub 上 **Kotlin 写、star > 20 的 mindmap 仓库只有 1 个**，还是个大作业 App，不是库。Android 这块没有"拿来即用"的成熟件。

| 方案 | star | 许可 | minSdk | 多根 | 结论 |
|---|---|---|---|---|---|
| **`MindMapGraphView`（现有）** | — | 自有 | 24 | ✅ | **保留**：Canvas 画树、双指缩放 0.2~3x、点节点折叠、字号档、读 `values/` 令牌 |
| GysoTreeView（`android-thinkmap-treeview`） | 550 | MIT | 21 | ❌ `TreeModel(root)` 单根 | 唯一像样的备选：RecyclerView 节点 + 四种方向布局 + 平滑缩放；但 Java、README 自述 Maven 件"很久没更新，请直接用 lib 里的代码"（要 vendor 进来改） |
| ThinkMap（`owant`） | 355 | Apache-2.0 | 低 | ❌ | 否决：2021-11 之后没再提交 |
| MindMapView（`hegleB`） | 8 | MIT | — | ❌ | 否决：太小、编辑向 |
| and_mindmap（`ttpho`） | 1 | MIT | **28** | ❌ | 否决：minSdk 超了，且只有 1 star |
| Compose 系（`mindmap-ui` 等） | <50 | — | — | ❌ | 否决：项目没有 Compose |

`MindMapGraphView` 已经干了这些事，换库只会丢功能：多根并排、折叠时以被点节点为锚不跳视野、命中区按 48dp 放大、`recite_font_level` 三档联动、`OverScroller` 惯性。它真正缺的是两件小事：夜间配色写死日间（`cRootBg` 等），以及 0.2x 缩放下没有 LOD（全量画文字）。

## 4. 落地建议

### 4.1 Web：`MindMapPane` 加一个"图"页签（只读）— 已落地 2026-11-16

```
MindMapPane
├── 大纲（现状，可编辑、是唯一写入口）
└── 图（markmap 只读：折叠 / 缩放 / 平移）
```

| 文件 | 职责 |
|---|---|
| `src/mindmap/tree.ts` | 资产 → markmap 节点（主题名当可见根）；`#path` 形式的节点 id、id ↔ 大纲 path 互转、内容签名 |
| `src/mindmap/render.ts` | 渲染参数：`treeLayout` + `createCardsTheme`（分支色用编辑器的紫系）、`colorScheme` 跟明暗 |
| `src/components/MindMapGraph.tsx` | 画布组件：挂载即建图、内容变了 `setTree`、明暗变了 `setOptions`（树与折叠状态保留）、尺寸变了 `fit()`、点节点抛 path |

行为细节：

* **图是"看"的地方，不承担编辑**：改字/增删仍然只在大纲里做，避免两套真相；
* **默认折到 2 层**：50 条一页全展开会缩到字看不清，先给骨架，用户自己点圆点展开；
* **点节点回大纲**：切回大纲、逐级展开祖先、滚到那一行并闪一下（`data-topic` / `data-path` 定位）；
* **筛选用同一套**：板块下拉与搜索仍然生效，图里的主题选择器只在命中结果里列；
* **依赖**：`@markmap/view`、`@markmap/render`、`@markmap/core`（要用 `MarkmapNode` 类型），**没有** `@markmap/parse` / `canvas` / `toolbar`。

### 4.2 Android：不引库，补短板 — 已落地 2026-11-16

| 补的 | 做法 |
|---|---|
| **分级绘制（LOD）** | `scale ≥ 0.6` 画整块多行文字；`0.22~0.6` 只描首行（`drawText` 取 `getLineEnd(0)`）；`< 0.22` 只剩色块，折叠徽标一并省掉。一页 1194 节点全展开不再逐条画多行布局 |
| **长按看全文** | 画布只抛 `onNodeLongPress`（带触感反馈），弹窗由宿主开 `FbDialog.text`（新布局 `dialog_fb_text.xml`，正文封顶六成屏高、超出滚动）。画布自己不弹窗，免得和缩放 / 拖动抢手势 |
| **转屏保状态** | `onSaveInstanceState` 存折叠集合、字号档、缩放与位移；恢复后先按新尺寸夹位置，**不再 fit**（`restoredState` 挡住 `onSizeChanged` 与 `setNodes` 里那次适应屏幕） |
| **布局缓存** | `LruCache<String, StaticLayout>(512)`，键是「层级桶 + 字号 + 正文」。展开 / 折叠 / 切字号时同一句不重复构建 |
| **缩放按钮** | 新增 `zoomBy(factor)`：以画布中心为锚，底部 `－ / ＋` 每次 25%，范围与手势一致（0.2~3 倍）。单指拖动、甩动惯性、双击空白切「适应屏幕 / 1:1」沿用原实现 |
| **多根分栏** | 见 §4.2.1。19~22 根不再竖排一列，按根顺序切 1~6 栏并排，栏数按画布比例挑 |
| **夜读** | 见 §4.2.2。标题栏右上角「夜读 / 日读」，整页（含系统栏）换深色，选择存库 |
| **徽标留白** | 折叠徽标画在节点外侧，内容宽度原来没算它，最右一列的徽标被屏幕边缘裁掉；分栏时把 `badgeSlot` 计入最右列宽度 |

#### 4.2.1 多根分栏

一页书十几个中心主题是常态（OCR 把「分配制度」切成三块很常见），竖排一列时整幅图的比例是 0.2 左右，
`fit` 被高度锁死，字小到看不清。做法：

* 根按**顺序**切到几栏（不按高度重排：同一页书里主题的先后是有意义的），每栏至少一根；
* **同一栏**里的根共用一套列宽（同深度对齐），不同栏互不影响——这样多切一栏不会把每棵树都撑宽；
* 栏数由 `MindMapLanePacker` 逐个试 1~6，按 `score = max(宽, 高 ÷ 画布高宽比)` 取最小：
  哪一维超出画布比例，哪一维就先被压到，score 小就意味着 fit 之后字大；
* 折叠 / 展开**不重算**栏数（否则点开一个分支整页重新分栏，视野大跳），换内容 / 换字号才重算；
* 转屏时栏数随视图状态保存，不重分。

用真实资产跑离线模拟（`recite_mindmap.json` 41 个主题、1080×1900 竖屏画布）：

| 页 | 根 | 旧 fit | 新 fit | 提升 |
|---|---|---|---|---|
| `d18` | 19 | 0.26 | 0.42 | **1.59×** |
| `d22` | 22 | 0.25 | 0.39 | **1.58×** |
| `d28` | 22 | 0.25 | 0.39 | 1.58× |

41 个主题里 **30 个仍是 1 栏**（根少、本来就接近竖屏比例，不动），11 个变 2 栏；fit 中位数 0.50 → 0.52。
即便分栏，19 根那页也到不了 0.6（一屏塞 50 个节点本来就不可能），所以 LOD 的首行模式仍是常态。

**真机（MuMu 12，1440×2560）实测**：19 根那页自动分 2 栏，内容宽高比贴合画布，不再是一条竖线；
夜读开关重进沿用，只看主干 / 展开全部来回切也不重排栏数。实测还抓到一个第一版没算到的细节：
折叠徽标画在节点 rect **外面**，内容宽度没留这块，fit 之后最右一列的「6」「7」正好被屏幕边缘切掉
（像素测量：内容右边界贴到 x=1439，屏宽 1440）。修法是分栏时把 `badgeSlot = 2×半径 + 2dp`
算进最右一列的宽度，修完右边界回到 contentPad（30px）以内。

#### 4.2.2 夜读

之前记的「夜间配色没做，因为背诵模块没有夜间」这条不成立了：**开关放在导图页自己身上**。
全屏看图的场景本来就独立于背诵列表，标题栏右上角一个「夜读 / 日读」，选择存 `settings`（key `mindmap_graph_night`），下次进来沿用。

* 一次换全部：画布底、节点块、连线、折叠徽标、标题栏、提示行、分割线、底部动作、状态栏 / 导航栏（含图标明暗）；
* 文字颜色是烤进 `StaticLayout` 的，换肤时整批 `evictAll()` 重排，否则会拿回白底配色的旧布局；
* 换肤**不动排版**：栏数、折叠状态、缩放位置都沿用。

配色映射（全部复用现有 `fb_night_*` 令牌，不新增颜色）：

| 元素 | 日间 | 夜间 |
|---|---|---|
| 画布底 | `fb_page_bg` | `fb_night_sheet_bg` |
| 中心主题块 / 字 | `fb_primary_soft` / `fb_primary` | `fb_night_tag_bg` / `fb_night_tag_text` |
| 分支·要点块 | `fb_card_bg` | `fb_night_card` |
| 分支字 / 要点字 | `fb_text_title` / `fb_text_secondary` | `fb_night_text` / `fb_night_text_body` |
| 连线 / 块描边 | `fb_tree_rail` | `fb_night_tree_rail` / `fb_night_circle_stroke`（对块底 1.73:1，比日间 1.6:1 略强） |

如果坚持"两端完全同款"，再走 WebView：`assets/mindmap/map.html` + 同一份 bundle，`evaluateJavascript` 传 JSON（1194 节点约 190KB，一次传完），主题用 query 参数。**不建议**：App 现在连 WebView 都没用过，为一个"鸟瞰"页引入整套 Chromium。

## 5. 代价与风险

| 项 | 数值 / 说明 |
|---|---|
| Web 体积 | 单独打包 351KB min / 114KB gzip；**接入后生产构建**：产物原始 643KB → 994KB（+351KB），gzip 206KB → 322KB（**+116KB**）。多出来的 `highlight`(177KB) / `notes-html`(57KB) 是 markmap 的懒加载 chunk，首屏不下载 |
| 许可 | markmap MIT，保留版权声明即可；simple-mind-map 若将来改用，需要在其文档页挂"基于 SimpleMindMap"声明 |
| 镜像滞后 | 本机 npm 源（npmmirror）只同步到 `1.1.0`，`1.1.1` 未同步；锁 `1.1.0`，别写 `^1.1.1` |
| **数据才是瓶颈** | 26/41 个主题 >3 根，最多 22 根——任何库画出来都是"扇形毛刺"。markmap 的 org-chart 在 19 根时直接压成一条线。**先把 `tools/mindmap/manual.json` 的碎片根合并做完（docs/15 P1），再谈布局美化** |
| 只读 ≠ 省事 | 用户在图上点节点会期待"能改"，所以图上要明确给"去大纲编辑"的落点，否则会被当成坏了 |

## 7. 一句话收尾

**库是够用的，但都不是"接上就完事"**：Web 端 markmap 是唯一真正适配我们多根数据的（且要绕开字符串 theme/layout、绕开 markdown 解析两个坑）；Android 端没有能替代现有实现的库，别为了"用库"把已经跑通的 596 行换掉。
