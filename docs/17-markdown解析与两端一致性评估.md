# 17 · Markdown 解析与两端一致性评估

> 背景：Web 端（局域网编辑器）输入时要支持 markdown，两端（Web 预览 / App）的解析展示要补齐、对齐。
> 本文盘点现状、列出缺口，给出选型结论与优先级，作为后续改造的依据。
>
> **决策更新（2026-11-22）**：`:::chart` / `:::figure` / 裸表格从未实际使用，已整体下线（0.5.1）——
> 缺口 2、4 与对应建议作废；两端解析面收窄为「段落 / Markdown 表格 / 图片」，后续补齐项见第 4 节。
>
> **决策更新（2026-11-23）**：行内 `**粗体**` / `` `代码` `` 已在 App 端补齐（`ui/InlineMarkdown.kt`，
> 材料段落 / 题干 / 表格单元格 / 背诵正文共用），缺口 1 关闭；背诵三页的正文改走
> `ReciteRichView`，段落 / 表格 / 图片与材料同一套块解析，挖空与行内格式在同一套 run 里渲染。

## 1. 现状盘点

两端都是**自研逐行解析器**，口径基本对齐（`:::figure` 的 layout/width/size、图片行、行尾 `{size=full}` 等写法两端认的是同一套）。

### App 端：`app/src/main/java/com/lytree/qbank/ui/MaterialRenderer.kt`

| 层面 | 现状 |
|---|---|
| 块级 | 段落、Markdown 表格（`\|` + 分隔行）、**裸表格**（制表符 / ≥2 空格对齐）、图片行、`:::chart`（ChartView 真自绘）、`:::figure` 图文块（5 种布局） |
| 行内 | 图片 + `**粗体**` + `` `代码` ``（`ui/InlineMarkdown.kt`，材料段落 / 题干 / 表格单元格 / 背诵正文共用）；`# 标题`、`- 列表`、`> 引用` 仍当普通段落 |
| 渲染 | 原生控件：TextView / FitTableLayout（列宽自适应 + 窄屏缩字号）/ ChartView 自绘 / AdaptiveImageView（原图 ×2 上限、点图看大图）；夜间配色、字号缩放全套跟随 |

### Web 端：`tools/webeditor/src/markdown.ts`（编辑器源码在 `tools/webeditor/`）

| 层面 | 现状 |
|---|---|
| 块级 | 段落、`\|` 表格、图片行、`:::chart`（**只渲染占位提示**「App 自绘图表」，不真画）、`:::figure`（与 App 同口径） |
| 行内 | 图片、`**粗体**`、`` `代码` ``、换行 |
| 渲染 | `innerHTML` + CSS；图片按「原图尺寸、宽了等比收到栏宽」排（2026-11-22 起不再 ×2 放大——那句内联 `maxWidth` 会让图冲出左栏被裁），App 侧仍是 `AdaptiveImageView` 的 ×2 上限 |
| 输入 | textarea + 工具栏（figure 排版按钮、插图、Ctrl+V 贴图）+「排版预览」开关；题干侧只有一行 `plain()` 摘要，无即时预览 |

## 2. 缺口与不一致清单（按影响排序）

| # | 缺口 | App | Web | 影响 |
|---|---|---|---|---|
| 1 | 行内 `**粗体**` / `` `代码` `` | **已补齐**（2026-11-23，`InlineMarkdown`） | 正常渲染 | 两端口径一致，老试卷里的粗体不再露源码 |
| 2 | 裸表格（tab / 多空格） | **已下线**（2026-11-22，从未使用） | 本就不支持 | 两端口径一致了：都只认 Markdown 竖线表格 |
| 3 | `#` 标题 / `- 列表` / `1. 列表` / `> 引用` | 不支持 | 不支持 | 用户按 markdown 习惯写，两端都露源码；AI 生成材料（带标题列表）导入必中招 |
| 4 | `:::chart` / `:::figure` | **已下线**（ChartView 已删） | 已下线 | 图表统一用截图配图；残留 `:::` 围栏按普通文字显示，不吞内容 |
| 5 | 网络图片 | 不加载 | 有提示不加载 | 一致（都不支持），仅提示口径不同，可不动 |
| 6 | 表格多行表头 `headerRows` | 只支持 0/1 | 只支持 1 | 低频，暂不动 |
| 7 | **数学公式（`$...$` / `$$...$$`）** | 不支持（原样显示 LaTeX 源码） | 不支持 | 数量关系 / 理科内容卷的硬需求：分式、根号、上下标在纯文本里没法看；AI 生成理科试卷时输出 LaTeX 是标配，导入即露源码 |

**结论：缺口 1 是「两端口径不一致」，先补齐；缺口 3 是「两端都缺」，一起加；缺口 7 是「两端都缺」且依赖第三方渲染内核，单独立项；缺口 2、4 随下线决策关闭。**

## 3. 选型评估

### 3.1 Web 端解析

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A. 继续自研增量扩展** | `markdown.ts` 已是同口径自研；加标题/列表/裸表格是几十行的增量；单换行、宽松表格等现有行为不变，**老试卷零回归** | 语法覆盖靠手写，遇到冷门写法要自己补 | ✅ 推荐 |
| B. 换 markdown-it / marked | 语法完整、生态成熟 | `:::chart`/`:::figure`/裸表格要写插件；默认规则（严格换行、表格需表头）与现有口径不同，**全部存量试卷要重新对拍**；新增依赖要过打包体积 | ❌ 不值得 |

### 3.2 App 端解析

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A. 继续扩展 MaterialRenderer** | 零依赖；行内格式用 Spannable 补上即可；表格/figure/夜间/字号缩放那套全保留 | CommonMark 全集永远凑不齐（但刷题场景用不到） | ✅ 推荐 |
| B. 引入 Markwon（commonmark-java） | 标准 CommonMark、Span 原生渲染 | `:::chart`/`:::figure` 要写自定义扩展节点；与 FitTableLayout 列宽自适应、笔迹锚点、AdaptiveImageView 的整合成本高；依赖 +300KB | ❌ 收益撑不起成本 |
| C. 两端都走 WebView 渲染 HTML | 一致性最强（同一段 HTML） | 材料左右分屏、手写笔迹锚点、夜间配色、字号缩放、本地图片加载器全部要重做；WebView 内存与首帧成本 | ❌ 工程量最大，否 |

### 3.3 数学公式（两端都缺，需引入渲染内核）

写法约定：行内 `$E=mc^2$`、块级 `$$...$$`（各占一行）；`\(...\)` / `\[...\]` 暂不认，减少误伤。
公式源是纯文本，随题目字段存储即可，**不涉及资源文件与导入链路改动**。

| 方案 | 说明 | 结论 |
|---|---|---|
| **Web：KaTeX** | 轻量（比 MathJax 小一个量级）、同步渲染快，适合预览里大量小公式；公式源先 `esc()` 再喂 KaTeX，关掉 `trust`，无 XSS 风险 | ✅ 推荐 |
| Web：MathJax | 语法覆盖最全 | 太重（首屏 MB 级），预览场景用不到全量 TeX；❌ 不采用 |
| **App：JLatexMath-Android** | 原生库，TeX → Bitmap/Drawable，可直接嵌 TextView 行内（Span）或当 ImageView 排块级公式，与现有 AdaptiveImageView / 夜间配色（可重着色）兼容；零 WebView | ✅ 推荐 |
| App：WebView + KaTeX（每个公式一个离线 WebView 渲染成图） | 与 Web 端**同内核同视觉** | 每个公式起一次渲染，滚动列表里开销大、生命周期管理麻烦；⚠️ 备选 |

**一致性口径**：两端内核不同（KaTeX vs JLatexMath），TeX 子集覆盖不完全一致——

1. 规范先限定常用子集：上下标、分式、根号、希腊字母、常见符号（≤ ≥ ≠ × ± ∑ ∫）、简单括号自适应；矩阵 / 化学式等冷门特性列为不支持。
2. 对拍用例里放一组公式样例，两端渲染结果只要求「结构正确」（分子分母、根号位置对），不追求像素级一致。
3. 解析顺序（两端同规则）：**先提取公式占位再走 markdown 行内解析**（粗体/代码/图片正则不得吞公式内容），渲染时回填——Web 端占位节点后调 KaTeX，App 端占位 Span 后用 JLatexMath 出图。

### 3.4 Web 端输入（「输入支持 markdown」）

| 方案 | 说明 | 结论 |
|---|---|---|
| **A. textarea + 工具栏 + 即时预览（增强现有）** | 现有 textarea 流（grow 自适应、贴图、figure 按钮）全保留：① 工具栏补「加粗 / 代码 / 表格 / 标题 / 列表」插入按钮；② 材料和题干的「排版预览」默认开或改为编辑框右侧实时小预览；③ 题干加与材料同款预览开关 | ✅ 推荐。改动集中在 `MaterialList.tsx` / `QuestionCard.tsx`，风险小 |
| B. 所见即所得（TipTap / Milkdown / CodeMirror） | 编辑即渲染 | 自定义 `:::chart`/`:::figure` 语法在 WYSIWYG 里很难表达；与现有贴图 / figure 按钮逻辑全部重写；包体积大涨；❌ 否 |
| C. 纯 textarea 不加预览 | 零改动 | 写 markdown 全靠脑内排版，错参（chart/figure）导入 App 才发现；⚠️ 最低限度，不满足诉求 |

## 4. 推荐路线

**总路线：两端继续自研增量扩展 + Web 输入侧增强现有 textarea 体验；不引入第三方 markdown 解析库（数学公式的渲染内核 KaTeX / JLatexMath 除外，见 3.3）。**

按优先级：

- ~~**P0 · App 补行内格式**~~：已完成（2026-11-23，`ui/InlineMarkdown.kt`），`**x**`→加粗 Span、`` `x` ``→等宽底色 Span，材料段落 / 题干 / 表格单元格 / 背诵正文共用；选项文字不在本次范围。
- ~~P0 · Web 补裸表格~~：随裸表格下线关闭。
- **P1 · 两端同加标题与列表**：`#`/`##` → 加粗放大段落；`-`/`*`/`1.` → 列表项（悬挂缩进）。规则先只认「行首」写法，避免把正文里的 `*` 误伤。
- **P1 · Web 输入增强**：工具栏加语法按钮（含「插入公式」$ 按钮与 `$$` 块按钮）+ 题干即时预览。
- **P1 · 数学公式展示（独立小项）**：Web 端接 KaTeX、App 端接 JLatexMath-Android，按 3.3 节口径先支持常用子集（上下标/分式/根号/希腊字母）；解析上两端同规则「先提取公式占位，再走 markdown 行内解析」。
- ~~P2 · Web 端真画 chart~~：随 `:::chart` 下线关闭。
- **P3 · 引用块、分隔线、删除线**：低频，按需再加。

## 5. 一致性保障

1. 写一份**语法规范小节**（并进 `docs/02-试卷格式规范.md`），把两端认的写法逐条列出，改语法先改文档。
2. **对拍用例**：一份覆盖全部语法的样例材料（标题/列表/粗体/表格/裸表格/chart/figure/图片），App 侧进 `MaterialStemTableTest` 那组单测，Web 侧进 vitest（`markdown.ts` 已可无 DOM 纯函数测），断言两端解析出的块结构一致。
3. 渐进启用：新增行内语法（粗体/代码）对存量试卷是「变好」，不会变坏；但标题/列表解析要防误伤——只认行首、且 `- ` 后必须有空格。

## 6. 工作量粗估

| 项 | 估时 |
|---|---|
| App 行内粗体/代码（段落+题干+选项+表格格） | 0.5~1 天 |
| Web 裸表格识别 | 0.5 天 |
| 两端标题/列表 | 1 天 |
| Web 输入工具栏 + 题干预览 | 1~2 天 |
| 数学公式：Web 接 KaTeX（解析占位 + 渲染回填） | 1 天 |
| 数学公式：App 接 JLatexMath-Android（占位 Span + 出图 + 夜间重着色） | 1.5~2 天 |
| Web chart 真渲染（SVG） | 1~2 天 |
| 语法规范文档 + 两端对拍用例（含公式样例） | 0.5~1 天 |
| **合计** | **约 6.5~10 天** |

主要风险：标题/列表的误伤（老试卷正文里有 `#`、`1.` 开头的行）——用 sample 试卷全量对拍后再上线；chart 两端绘图的视觉差异（不追求像素级一致，数据口径一致即可）。
